# 板块与成分股历史存储方案

更新：2026-09-06。状态：方案已确认，存储扩展、迁移及查询接口待实现。本次仅补充设计，不代表已经创建三家板块表、开启每日采集或补齐历史成分。

本文补充 [多数据源接入方案](../../openspec/changes/archive/2026-09-06-add-multi-source-market-data/design.md)。现有线上接口能力见 [providers 文档](../api/providers.md)，现有可执行表结构仍以 [ClickHouse 存储文档](../storage/clickhouse.md#infinity_markettdx_block_snapshots) 为准。

## 已确认的决策

1. TDX、同花顺、东方财富使用三套物理表，不使用一组通用表混存，也不通过 `source/provider` 列区分三家。
2. 三套表放在现有 `infinity_market` 数据库，按实际支持的板块范围分别采集、写入、订正和查询。
3. 第一版每天保存完整的板块定义及成分名单。即使与前一天相同，也独立保存当天的完整快照。
4. 成分明细只保留快照标识、板块标识、股票市场和代码，不重复保存股票名称、价格、成交量、涨跌幅、涨停原因等信息。
5. 暂不采用 baseline 加进出事件、有效期区间或跨日内容哈希复用。进出变化由两天完整名单做集合差得到，不另建变更事件表。
6. 查询以 ClickHouse 为准；原始接口响应或离线文件保留在本地归档，用于校验、重放和订正，不作为上层日常查询格式。

以上取代讨论过程中提出的“按板块去重快照、每日只保存引用”备选方案。可以保留同一日同一批数据重试的幂等校验，但不能将其变成跨日复用成员明细。

## 三套物理表

| 用途 | TDX | 同花顺 | 东方财富 |
| --- | --- | --- | --- |
| 每日完整快照记录 | `tdx_block_snapshots` | `ths_block_snapshots` | `dfcf_block_snapshots` |
| 快照中的板块定义 | `tdx_block_definitions` | `ths_block_definitions` | `dfcf_block_definitions` |
| 快照中的成分关系 | `tdx_block_memberships` | `ths_block_memberships` | `dfcf_block_memberships` |

东方财富存储前缀采用已确认的 `dfcf_`；现有 Go 包及在线 provider ID 仍为 `eastmoney`，由服务端显式映射到对应表，不为此改名或允许客户端任意指定表名。

三套表的基础字段语义保持一致，必要的体系特有字段各自扩展。共用 Go 校验和辅助代码不改变物理隔离。板块体系与采集渠道也不同：经其他数据服务获取的 TDX 板块仍属于 TDX 体系，输入冲突由 marketd 在写入前解决。

同名板块不自动合并。指数行情必须关联本体系的指数身份，不能使用 TDX 指数配合同花顺成员。复盘材料整理的题材、选股及归因继续独立保存，不充当三家板块的完整成分名单。

## 目标字段与身份

以下为每日快照的目标逻辑结构；具体增量 DDL 与 TDX 兼容方案由后续存储变更确定。

| 表 | 最小信息 | 逻辑身份 |
| --- | --- | --- |
| `*_block_snapshots` | `trade_date`、`block_id`、`snapshot_id`、`observed_at`、`snapshot_time`、`member_count` | 每个板块每天一份有效完整快照：`trade_date + block_id` |
| `*_block_definitions` | `snapshot_id`、`block_id`、板块名称、类别；已有证据时保存对应指数市场及代码 | `snapshot_id + block_id` |
| `*_block_memberships` | `snapshot_id`、`block_id`、`market`、`symbol` | `snapshot_id + block_id + market + symbol` |

- `block_id` 是体系内稳定标识，必要时包含板块类别或自定义范围；不能以展示名称或抓取列表序号充当长期身份。现有 TDX 文件解析产生的序号/名称标识需要先核对稳定映射，不能直接当作已验证的指数代码。
- `trade_date` 是名单所属交易日期，`observed_at` 是实际观测或获取时间，时间统一使用 Asia/Shanghai。今天取得的历史名单不能被记成今天的市场状态，也不能把今天取得的当前名单倒填到过去。实施时保留既有 TDX 排序键，将新 daily 记录的 `snapshot_time` 用作发布时间（API 名称为 `published_at`），与观测时间分开，以便订正旧观测日期。旧 client-local 记录语义不变。
- `snapshot_id` 标识某日某板块的一份完整内容，日期和板块身份必须参与其身份构造。同一日相同输入可幂等重试；不同日期即使内容一致，也对应不同快照；同日内容订正生成新快照。
- 板块名称与类别随快照保存，避免用今天的名称覆盖过去。没有核验到指数代码时保持未知，不按名称或号码猜测。
- 成员按证券身份去重。价格、页面排序、展示排名不是成员身份，不作为成分变更依据。市场事实不新增 `source`、`version`、`updated_at` 列。

## 每日采集、发布和订正

每日固定观测时间采集一次；具体时间按上游更新节奏配置，不能把“收盘后抓到”解释为已证明其精确收盘时点状态。默认不保存盘中每一次请求的成员名单。

以一个板块为完整性校验和发布单位：

1. 获取定义及全部成员分页，校验返回身份、日期、分页完整性、成员唯一性，以及上游提供的总数。解析错误或分页失败不能被转换成空名单。
2. 为当天完整内容生成快照标识，先写定义和全部成员；确认写入及数量校验成功后，最后发布当天有效快照记录。查询只选择已发布的快照，不能读取尚未发布的明细。
3. 未发生变化的板块也保存当天全量，不能只指向昨天的成员。采集失败只记录到已有 `task_runs`、`data_quality_issues`，不得伪造当天成功快照。
4. 同一板块同一天的写入由 marketd 串行处理。已有不同内容时必须走明确的订正流程，不能让普通重试或旧批次重放覆盖已订正结果。
5. 订正时先写新快照的完整内容，确认完整后切换当天有效快照记录，不在旧名单上逐条增删。旧快照中的多余成员不会因此进入新结果，其他日期不受影响。

沿用 `ReplacingMergeTree` 的项目约定；当日有效记录的查询必须按逻辑键消除重复，不能依赖后台合并已经发生。发布顺序是应用写入约束，不宣称 ClickHouse 的跨表写入具有原子事务；未发布内容不参与业务查询。

一个板块采集成功不等于整家目录完整。整次任务必须记录预期范围、成功及缺失板块；未在不完整目录中出现的板块不能据此判为已撤销。只有上游明确返回有效的完整空名单时，才发布成员数为零的快照，成员表没有行本身不证明该板块为空。

## 历史补录与查询

- 历史导入与每日在线采集使用同样的最终字段、完整性校验和发布流程。历史数据须有可核验的所属日期；不能仅凭当前文件的导入时间推断其历史有效日期。
- 获取不到的日期明确返回缺失，不能默认采用昨天、今天或另一体系的名单。若上层显式请求最近一次观测，必须返回其实际日期，不冒充目标日期的历史成分。
- 查询某日某板块：先按日期和板块找到有效快照，再读取对应定义和完整成员；查询某股当日归属则只匹配当日有效快照中的成员。
- 比较两天进出：分别读取两天完整成员集合再做差，只表示两次观测之间的变化，不推断官方加入/退出的准确生效日期。任一天缺失时不生成确定的进出结论。
- 板块历史 K 线、当前成分、历史成分是不同能力。没有历史成员数据不能借指数历史反推完整名单，也不能据此承诺覆盖 2016-01-01 至今。
- 在线 provider 读取不隐式落库；只有显式导入/刷新任务写入。存储查询保持经 querier 执行，ClickHouse 读取 SQL 仅放在 `internal/clickhouse/query.go`。

## 容量与第一版取舍

成分行数的估算公式为：各体系逐日所有板块的成员数之和。股票可属于多个板块，不能只用全市场股票数量估算成分关系数量。

例如每家 1,000 个板块、平均 100 个成员、每年 250 个交易日，三家保存十年会产生约 7.5 亿条成分行。这只是参数示例，不是当前实际规模，更不是磁盘占用结论。成分行是精简关系字段，不应按包含名称、行情或原文的宽行估算。

第一版不为假设的容量压力引入事件回放或跨日去重。使用实际样本测量成员数量、写入量、压缩后磁盘大小、历史查询延迟和每日增长，再判断是否需要优化。首次迁移先 dry-run 和代表性批次验收，不直接按假设启动十年全量导入。

## 实施边界

本方案是在线数据源接入之后的独立存储变更。沿用既有 Store、事实表规范和 ops 记录，TDX 旧表需要非破坏性迁移计划；不能执行 DROP、TRUNCATE、DETACH 或破坏性表替换。在线成分采集、定时任务和历史回填须各自验证来源、日期及覆盖，不由指数日线接口隐式触发。

## 验收标准

- 三家同名板块分别落入对应物理表，查询和订正互不影响。
- 连续两天成员相同仍各有独立全量快照；重复导入同一天相同内容不会产生重复逻辑成员。
- 成员增加、减少、完整空名单和采集失败四种情况能明确区分。
- 分页或成员写入失败不发布半份快照，也不提前切换已有有效快照。
- 同日整份订正不残留旧成员，不修改其他日期；旧任务不能覆盖订正。
- 板块改名不改变稳定身份，页面排序变化不形成进出事件。
- 历史所属日期与实际观测时间分离，查询缺失日期不偷偷回退或跨体系填充。
- 报告真实样本的压缩后容量和查询耗时，不能用假设行数宣称存储验收完成。
