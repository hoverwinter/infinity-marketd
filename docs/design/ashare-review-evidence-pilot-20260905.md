## 实际材料问题

抽样覆盖 2016-01-04、2016-03-16、2018-06-05、2020-02-03、2021-09-15、2023-09-18、2023-09-19、2026-09-04，共 8 个日期、63 张湖南人截图材料。提取 293 个按日期/代码/事件归组的候选，其中 88 个通过首版筛查；本轮只对照两张原图确认并写入其中 49 个，另 39 个筛查通过的候选也没有自动写入。这是抽样结果，不是全量恢复率。

发现的主要问题：

- **OCR ready 不等于表格已解析。** 2023-09-18 主表结果标为 `taoguba/limit_up_list`，置信度约 0.87，但 `structured.rows=[]`。全文阅读顺序不稳定，必须利用原始 bbox 恢复行列。
- **工作区日期不能直接作为图片日期。** 2016-01-04 部分材料图内明确是 2015-12-31；2016-03-16 也发现日期冲突。首版拦截，不修改原始材料归档或悄悄改归属。原补数报告的 complete 只表明当时的管线审计通过，不能视为图内语义核验通过。
- **一张图可能同时包含连板概览、题材明细、炸板表和大涨榜。** 连板概览与题材明细可能使用不同粒度的原因；大涨超过 10% 不一定涨停。不能按出现股票代码就生成事件。
- **跨截图续表缺少日期和表头。** 2020-02-03 第二张续表暂不自动拼接，早期旧版式也暂不支持。
- **当前名称主数据不保证历史完整。** 部分名称对不上可能是历史 ST/改名区间不全，也可能是 OCR 错字；首版一律待核，不用当前简称替换历史名称。
- **底表仍有事件和连板缺口。** 例如 2023-09-18 原图安泰集团标 3 板，当前底表为 1 板；本轮只补该股原因，没有把原因核验扩大为连板订正。缺失事件、严格连板和 ST 口径需要独立核验。

三日期主试点的 113 条候选中有 12 条炸板记录，均未写入。五日期补充样本的 180 条候选也全部保持为计划。原因识别错位、低置信、已有事实冲突等情况保留在报告中；多个问题可同时属于同一候选。

## 实现边界

Infinity/quman：

- `ashare/historical_review/evidence/table_extraction.py`：按有日期的湖南人表头和 bbox 提取行，保留置信度/歧义。不是通用文档或 LLM 解析器。
- `ashare/historical_review/evidence/corrections.py`：与历史名称和 marketd 当前事件核对，产生计划；显式选择后发布。

- `ashare/marketd_client.py`：分页读取最终事件、调用鉴权补录接口；不直接连接 ClickHouse。

Marketd：继续使用既有 Go `POST /api/console/imports/limit-review-corrections` 和 `internal/ingest/limit_review.go`。没有新增服务、事实表、来源列、Python 依赖或部分字段 patch API。

**首版仅允许补空值：** 原因必须为空；主题必须为空或等于旧快照的“未分类”。主题只取明确题材分组标题，“市场连板股”“其他热点”“其他个股”不作为主题。标签不自动拆分。已有不同值、未落库事件、炸板事件均拒绝进入发布。

## 写入保护

1. 计划保留原图、OCR、工作区的 SHA-256，行坐标、提取值和整行 before-image。
2. 必须显式选择候选 ID 并填写核验说明，不提供“全部 OCR 自动写入”。本次由 Codex 对照两张原图核验后选择 49 条，核验说明保留在 ops/report。
3. 发布前重读 HTTP 最终事件与计划比较；输入文件或已有事实改变则拒绝。出现未知表字段也拒绝，避免整行替换时丢字段。
4. 先调用 Go dry-run；显式 execute 时，再检查 before-image，按日期串行发送完整行。
5. 每日写后回读所有字段，留存任务 ID、前后值及错误。结果不确定时不自动重试，不删除历史记录。

这是应用层的读、核对、写入流程，**不是跨进程事务或分布式锁**。仍需避免其他导入/订正任务并发处理同日同股。多日任务可能部分成功，应按报告回读后处理，不能盲目重放。
